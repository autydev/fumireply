# Feature Specification: 送信側メディア添付 — オペレーターから顧客への画像送信

**Feature Branch**: `010-outbound-media`
**Created**: 2026-07-20
**Status**: Draft
**Input**: User description: 送信側メディア添付 (issue #82): オペレーターがスレッドの返信フォームから画像 (jpeg/png/gif/webp、1 送信 1 枚) を添付して顧客の Messenger に送信できるようにする。送信画像は送信時に自社側へ永続保存・記録し、自社スレッド UI の outbound バブルに表示する (echo による backfill は期待できない)。テキスト+画像同時入力はテキスト→画像の順に 2 メッセージ送信。video/audio/file/sticker 送信・複数枚同時添付・画像加工・AI 下書きへの画像組み込みはスコープ外。親 Issue: autydev/fumireply#82

## User Scenarios & Testing *(mandatory)*

### User Story 1 - オペレーターが画像を添付して顧客に送信できる (Priority: P1)

顧客対応では「商品写真を送ってほしい」「案内図を見せてほしい」といった、画像で返答すべき場面がある。現状の fumireply はテキスト返信しかできないため、オペレーターは画像を送るためだけに Meta 側インボックスへ移動せざるを得ない。本ストーリーでは、スレッドの返信フォームから画像を 1 枚添付して送信すると、顧客の Messenger にその画像が届き、同じ画像が自社スレッドの送信側バブルにも表示されるようにする。

**Why this priority**: 009 で受信側の画像対応が完了し、残る「fumireply を一次窓口として成立させる」うえでの最大の欠落が送信側の画像。これ単体で「画像を添付 → 送信 → 顧客に届く → 自社でも見える」という完結した価値を提供できるため P1。

**Independent Test**: オペレーターがスレッドで画像を 1 枚添付して送信し、(1) 顧客役アカウントの Messenger に画像が届くこと、(2) 自社スレッドの送信側バブルにその画像がサムネイル表示されクリックで原寸表示できること、(3) 画面の自動更新後や再訪問後も表示が安定していることを確認できる。

**Acceptance Scenarios**:

1. **Given** 返信可能な会話 (最終受信から 24 時間以内) が存在する、**When** オペレーターが画像を 1 枚添付して送信する、**Then** 顧客の Messenger にその画像が届き、送信は成功として記録される
2. **Given** 画像の送信が成功した、**When** オペレーターが自社スレッドを見る、**Then** 送信側バブルにその画像がサムネイル表示され、クリックで原寸表示できる (受信画像と同等の表示品質)
3. **Given** 画像を添付済みの状態、**When** オペレーターが送信前にプレビューを確認する、**Then** 添付した画像のプレビューが表示され、送信せずに取り消すこともできる
4. **Given** 送信した画像メッセージがある、**When** 時間が経過して画面が自動更新される・スレッドを開き直す、**Then** 画像は引き続き表示される (表示が壊れたり消えたりしない)

---

### User Story 2 - テキストと画像を同時に送信できる (Priority: P2)

オペレーターは「こちらが該当の商品です」という説明文と画像をセットで送りたいことが多い。配信基盤の制約上テキストと画像は 1 通に同居できないため、テキスト → 画像の順に 2 通のメッセージとして送信する。

**Why this priority**: US1 (画像単体送信) だけでも価値は完結するが、実運用では説明文とセットで送るケースが大半のため、体験として早期に揃えたい。

**Independent Test**: 返信フォームにテキストを入力しつつ画像を添付して送信し、顧客の Messenger にテキスト → 画像の順で 2 通届くこと、自社スレッドにも 2 つのメッセージとして順に表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 返信可能な会話が存在する、**When** オペレーターがテキストを入力し画像も添付して送信する、**Then** 顧客にはテキスト → 画像の順で 2 通のメッセージが届く
2. **Given** テキスト+画像の送信を行った、**When** 自社スレッドを見る、**Then** テキストと画像がそれぞれ独立したメッセージとして順に表示され、それぞれの送信結果 (成功/失敗) を個別に確認できる
3. **Given** テキストの送信は成功したが画像の送信が失敗した、**When** オペレーターがスレッドを見る、**Then** テキストは送信済み、画像は失敗として区別して表示され、どこまで届いたかが分かる

---

### User Story 3 - 送信できない場合は理由が分かり、誤送信・事故が起きない (Priority: P2)

画像送信には失敗がつきものである (対応外の形式・サイズ超過・アップロード失敗・配信失敗・返信期限切れ)。本ストーリーでは、失敗をオペレーターに明確にフィードバックし、また対応外のファイルや期限切れの会話への添付をそもそも受け付けないことで、無言の失敗や誤送信を防ぐ。

**Why this priority**: US1 の品質を支える受け皿。失敗が黙って握りつぶされると「顧客に届いたつもり」という最悪の運用事故につながるため、機能リリースと同時に必要。

**Independent Test**: 対応外形式のファイル・上限超過サイズの画像・返信期限切れの会話のそれぞれで添付/送信を試み、適切なエラー表示や操作の無効化が行われることを確認できる。

**Acceptance Scenarios**:

1. **Given** オペレーターが対応外の形式 (画像以外・非対応の画像形式) のファイルを選択した、**When** 添付しようとする、**Then** その場で対応外である旨が表示され、添付されない
2. **Given** サイズ上限を超える画像を選択した、**When** 添付しようとする、**Then** その場で上限超過である旨が表示され、添付されない
3. **Given** 最終受信から 24 時間を超えた会話を開いている、**When** 返信フォームを見る、**Then** テキストと同様に画像添付・送信もできない状態になっている
4. **Given** 画像の配信が失敗した (顧客に届かなかった)、**When** オペレーターがスレッドを見る、**Then** 該当メッセージが失敗として表示され、失敗理由の区分 (期限切れ・認証エラー・一時エラー等) が既存のテキスト送信失敗と同様に分かる
5. **Given** 送信が失敗した、**When** オペレーターが同じ画像で再度送信を試みる、**Then** 画像を選び直さずに再送信できる、または再添付が簡単に行える

---

### Edge Cases

- 返信期限 (最終受信から 24 時間) を過ぎた会話 — テキストと同一のポリシーで添付・送信とも不可。判定は送信実行時にも再検証する (フォームを開いたまま期限が切れるケース)
- 対応外形式・サイズ超過 — 選択時に即時拒否し、送信実行時にもサーバー側で再検証する (二重防御)
- アップロードは完了したが送信せずに離脱した — 未送信の画像データが残るが顧客には何も届かない。残存データの掃除は保持期間ポリシー検討 (#78) に合流し、本機能では許容する
- 画像の配信が失敗した — メッセージは失敗として記録・表示され、画像データ自体は保持されるため再送を妨げない
- 外部送信の取り込み (echo) との整合 — fumireply から送信した画像メッセージが echo 経由で二重に表示されたり、添付情報が消えたりしないこと (既存の重複排除の仕組みに整合させる)
- 他の会話・他のテナントに属する画像参照の持ち込み — 送信時に参照の帰属を検証し、自会話の事前アップロード分以外は拒否する
- メディアストレージが未設定の環境 — 画像添付機能は無効化し、テキスト送信は従来どおり動作する
- テキスト+画像送信の部分失敗 — 2 通は独立したメッセージとして扱い、それぞれの成否を個別に記録・表示する (自動ロールバックはしない)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: オペレーターはスレッドの返信フォームから画像ファイルを 1 送信につき 1 枚添付できる。対応形式は jpeg / png / gif / webp とする
- **FR-002**: 添付できる画像のサイズ上限は 25MB とする (受信側 009 の保存上限と整合)。形式・サイズの検証は選択時 (即時フィードバック) と送信実行時 (サーバー側) の両方で行う
- **FR-003**: 添付済み画像は送信前にプレビュー表示され、送信せずに取り消せる
- **FR-004**: 送信された画像は顧客の Messenger に画像として届く
- **FR-005**: 送信画像は送信時点で自社管理の永続ストレージに保存され、メッセージの添付情報として記録される。外部からの取り込み (echo) による事後補完には依存しない
- **FR-006**: 自社スレッド UI は送信画像を受信画像と同等の品質で表示する (サムネイル + クリックで原寸表示)。画面の自動更新・再訪問後も表示が安定していること
- **FR-007**: テキストと画像が同時に入力された場合、テキスト → 画像の順で 2 通のメッセージとして送信する。各メッセージは独立に成功/失敗を記録し、部分失敗時もどこまで届いたかが UI から分かる
- **FR-008**: 画像メッセージの送信状態 (送信中/成功/失敗) と失敗理由の区分は、既存のテキスト送信と同じ枠組みで記録・表示する
- **FR-009**: 返信期限 (最終受信から 24 時間) のポリシーはテキスト送信と同一に適用する。期限外では添付操作を無効化し、送信実行時にも拒否する
- **FR-010**: 事前アップロードされた画像の参照は、そのオペレーターが権限を持つテナント・会話に帰属するものだけを送信に使用できる。帰属外の参照の持ち込みは拒否し、拒否は運用ログから確認できる
- **FR-011**: 送信画像へのアクセスは認証済みかつ該当テナントの運営者に限定する。認可を伴わない恒久公開 URL で配信しない (受信側 009 と同一ポリシー)。配信基盤への受け渡しに用いる一時的な参照は短命とする
- **FR-012**: fumireply から送信した画像メッセージは、echo 経由の取り込みと重複せず 1 件のメッセージとして表示され、添付情報が失われない
- **FR-013**: 画像のアップロード・送信の成功・失敗を区別できる構造化ログイベントを既存の命名規約に沿って出力し、CloudWatch Logs Insights で件数を集計可能にする。カスタムメトリクスやアラートは追加しない
- **FR-014**: メディアストレージが未設定の環境では画像添付機能を無効化し、テキスト送信の挙動には影響を与えない
- **FR-015**: 本機能は既存の AI 下書き生成・未返信バッチ判定・下書き却下 (送信時 dismiss) の挙動を変えない。画像のみの送信もテキスト送信と同様に「返信した」として扱われる

### Key Entities *(include if feature involves data)*

- **メッセージ (Message)**: 既存エンティティ。送信側 (outbound) メッセージも受信側と同じ形式の添付情報を持てるようになる。テキスト+画像の同時送信は 2 件の独立したメッセージになる
- **添付 (Attachment)**: 009 で定義済みの、メッセージに属する添付情報。本機能では送信側メッセージにも送信時点で記録される (形式は受信側と共通)
- **事前アップロード (Pre-upload)**: 送信操作に先立ってオペレーターが自社ストレージへ預けた画像。テナント・会話に帰属し、送信実行時に帰属が検証される。送信されなかった場合は未使用のまま残る (掃除は #78)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: オペレーターが返信フォームから画像を添付して送信すると、正常系 (返信可能な会話・対応形式・上限内サイズ) では 99% 以上が顧客の Messenger に届く
- **SC-002**: 送信した画像は送信直後から自社スレッドに表示され、画面の自動更新や再訪問後も表示できなくなるケースが 0 件である
- **SC-003**: fumireply から送信した画像メッセージについて、スレッド上の二重表示・添付情報の消失が 0 件である (echo 取り込みとの整合)
- **SC-004**: 他テナント・他会話に帰属する画像を送信に使用できたケースが 0 件である
- **SC-005**: テキスト+画像の同時送信で、部分失敗時に「どこまで届いたか」が UI 上で判別できないケースが 0 件である
- **SC-006**: 画像を送るために Meta 側インボックスへ移動する運用が解消される (リリース後、画像送信起因の Meta インボックス併用がなくなる)

## Assumptions

- 送信画像の保存先は受信側 (009) と同じ自社管理オブジェクトストレージ・同じ添付情報形式を再利用する。保存キーの構造など具体設計は計画フェーズで確定する (親 Issue #82 に設計案あり)
- 画像ファイルのアップロードは、アプリケーションサーバーを経由させるとペイロード上限の制約を受けるため、ブラウザからストレージへ直接預ける方式を前提とする。具体的な方式は計画フェーズで確定する
- 配信基盤 (Meta Send API) への画像の受け渡し方式は計画フェーズで確定する。既定案は短命な参照 URL の受け渡し (issue #82 D3)。テキストと添付が 1 通に同居できないという配信基盤の制約により、テキスト+画像は 2 通送信とする
- サイズ上限は受信側と揃えて 25MB とする。配信基盤側の画像上限がこれより小さいことが計画フェーズで判明した場合は、その値まで引き下げる
- 送信されなかった事前アップロード画像・送信失敗後に残る画像データの掃除 (ライフサイクル) は #78 (保持期間ポリシー) に合流し、本機能では実施しない
- 返信期限 (24 時間ウィンドウ) の判定・失敗理由の区分・送信状態の枠組みは既存テキスト送信のものを再利用し、新しいポリシーは導入しない
- video / audio / file / sticker の送信、複数枚同時添付、画像の加工 (リサイズ・圧縮・注釈)、AI 下書きへの画像組み込みはスコープ外とする。複数枚送りたい場合は複数回の送信で代替する
- 送信画像は顧客とのやり取りの一部として、受信メディアと同じテナント分離・アクセス制御のポリシーで扱う
