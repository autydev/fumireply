SESSION / AUTH 解説

「すぐログアウトされる」のはなぜか
— セッション管理の仕組みと直し方

fumireply アプリ（TanStack Start + Supabase Auth + AWS Lambda 構成）における、ログイン直後に弾かれてしまう現象を、仕組みから丁寧に解説します。「Lambda で Web をやっているから」という要素も、結論から言うと 関係あります。

この文書の要点（30秒版） 1画面を開くと複数のサーバー処理が同時に走ります。アクセストークンが切れた瞬間、それらが同じリフレッシュトークンで一斉に更新をかけるのですが、Supabase はリフレッシュトークンを1回使ったら捨てる（ローテーション）方式なので、勝つのは1本だけ。残りは「無効」と判定されてログイン画面へ飛ばされます。さらに Lambda はリクエストごとに別インスタンスで動く（状態を共有しない）ため、この競合を防ぐ仕組みが効きにくい ── これが根本原因です。

1現在のセッション管理

fumireply は独自のセッションテーブルやセッション用の署名鍵を持っていません。認証は Supabase Auth の JWT 方式にまるごと乗っています。仕組みはこうです。

トークンは2種類、Cookie に保存

ログインに成功すると、Supabase が2つのトークンを発行し、ブラウザの httpOnly Cookie に保存します。

トークンCookie 名寿命 (maxAge)役割
アクセストークンsb-access-token3600秒 = 1時間「この人は本人」を証明する短命の入館証。毎リクエストで提示する。
リフレッシュトークンsb-refresh-token2592000秒 = 30日アクセストークンが切れたとき、新しいものと交換するための長命な引換券。

Cookie 属性は全箇所で統一：httpOnly / secure / sameSite:'lax' / path:'/'（domain 未指定＝ホストオンリー）。

毎リクエストで検証する「認証ミドルウェア」

サーバー側の各処理（会話一覧の取得、ページ状態の確認…）には authMiddleware（app/src/server/middleware/auth-middleware.ts）が付いていて、実行前に必ずこの流れを通します。

  1. Cookie から sb-access-token を取り出す → 無ければ即 /login。
  2. アクセストークンを Supabase に問い合わせて検証（verifyAccessToken）。
  3. 検証に失敗（＝期限切れ等）したら、sb-refresh-token を使って 新しいトークンに交換（refreshSession）。
  4. 交換で得た新トークンを Cookie に上書き保存し直す（setCookie）。
  5. それでもダメなら /login へリダイレクト（＝ログアウト）。

つまり「期限切れは自動リフレッシュで救う」設計自体は正しいのですが、複数の処理が同時にリフレッシュしたときの調整（排他制御）が無いのがこの後の問題につながります。

「Lambda で Web」という土台

このアプリのサーバー処理は AWS Lambda 上で動いています（terraform/modules/app-lambda、メモリ 1024MB / タイムアウト 30秒、同時実行数の予約なし＝オンデマンドで自動スケール）。ここが効いてきます。

  • ステートレス（状態を持たない）：Lambda は原則リクエストが来るたびに実行される関数で、処理の間でメモリを共有しません。「今リフレッシュ中だから待って」という共有ロックをアプリのメモリ上に置けない。
  • 同時実行＝別インスタンス：ブラウザが1画面で5本のリクエストを同時に送ると、AWS はそれを別々の Lambda インスタンスで並行処理することがあります。5つの処理はお互いの存在を知りません。

この「共有状態が無い・並行で走る」性質が、次章のレース（競合）を起こりやすくし、単純なメモリ内ロックでは直しきれない理由にもなります。

2何が問題か？

原因は大小3つあります。A 本命 が主犯、BC が悪化要因です。

A リフレッシュトークンのローテーション競合（本命）

Supabase のリフレッシュトークンは ワンタイムです。1回使って新トークンに交換すると、元のリフレッシュトークンは即座に無効になります（＝ローテーション）。盗まれたトークンの再利用を防ぐためのセキュリティ仕様です。

ところが fumireply では、1画面を開くと checkConnectedPagesFn・会話一覧・ページ状態…といった処理が並列に走ります。アクセストークンが切れた瞬間、これらが全員同じ1本のリフレッシュトークンで同時に交換をかけます。

最初に交換できた1本だけが勝ち、残りは「もう無効なトークンです（invalid_grant）」と拒否され、ログイン画面へ飛ばされます。さらに悪いことに、成功した処理もバラバラのタイミングで別々の新 Cookie を書き込むため、最終的にブラウザに残る Cookie が既にローテーション済み（無効）のものになり、次のリクエストでまたログアウト、という連鎖が起きます。

Lambda がここで効く もし全処理が「1つのサーバーの1つのメモリ」で動いていれば、「今リフレッシュ中だから他は待つ」というロック（デデュープ）で防げます。しかし Lambda では処理が別インスタンスに散るため、アプリのメモリ内ロックはインスタンスをまたいで効きません。「Lambda で Web をやっているから」という要素は、ここで確かに効いています。

問題のコードはここ

app/src/server/middleware/auth-middleware.ts（赤ハイライトが問題行）

24  let user = await verifyAccessToken(accessToken)
26  if (!user) {                                // ← アクセストークン失効
27    const refreshToken = getCookie('sb-refresh-token')  // 全処理が同じ RT0 を読む
31    const refreshed = await refreshSession(refreshToken)  ★問題① 調整なしで一斉に RT0 を交換
32    if (!refreshed) { throw redirect({ to: '/login' }) }  // 2本目以降は invalid_grant→ここでログアウト
35    setCookie('sb-access-token',  refreshed.accessToken,  ...)  ★問題② 各処理が別々の新 Cookie を
42    setCookie('sb-refresh-token', refreshed.refreshToken, ...)     上書き→無効トークンが最後に残りうる
49    user = refreshed.user
50  }

問題①（31行目）：並列に走る各リクエストが、互いを知らないまま同じ RT0 で交換をかける。排他制御・デデュープが無い。

問題②（35–48行目）：成功した処理がそれぞれ独立に Cookie を上書きする。順序次第で、ブラウザに最後まで残る Cookie が既にローテーション済み（無効）のトークンになる。

「1本化」を差し込むべき場所

app/src/server/services/auth.ts:30-41 の refreshSession は supabase.auth.refreshSession() をそのまま叩くだけで、同一トークンの同時実行をまとめる仕掛けがありません。修正（ロック／デデュープ／reuse interval の利用）はこの関数か、その呼び出し元 auth-middleware.ts:31 に入れます。

30  export async function refreshSession(refreshToken) {
31    const supabase = getSupabaseClient()
33    const { data, error } = await supabase.auth.refreshSession({ refresh_token: refreshToken })
      // ↑ ここに来る前に「同じ RT0 の交換は1本にまとめる」処理が必要
34    if (error || !data.session || !data.user) return null
      ...
41  }

B Supabase クライアントの状態共有

getSupabaseClient()（app/src/server/services/auth.ts）は Lambda インスタンス内で 使い回しの単一インスタンス（singleton）を作りますが、生成オプションで persistSession / autoRefreshToken を無効化していません（＝デフォルトの true のまま）。

このため、同じインスタンスで並行する複数リクエスト（別テナントを含む）が、1つのクライアントの内部セッション状態を共有してしまいます。ログアウト処理の signOut({ scope: 'global' }) の影響が想定外に広がる恐れもあります。実際、E2E テスト用のシードでは persistSession:false, autoRefreshToken:false を明示しているのに、本番ランタイム側だけ指定漏れという不整合があります。

C 一過性エラーと「本当に無効」の混同

verifyAccessToken は、error でも user が空でも一律 null を返します。つまり「トークンが本当に無効」と「Supabase に一瞬つながらなかった（15秒タイムアウト等のネットワーク不調）」を区別していません。一過性の障害でも即ログアウト扱いになり、続くリフレッシュも一時失敗すれば /login へ。Lambda のコールドスタートや外部通信の揺らぎと相まって、体感の「突然ログアウト」を増やします。

3解決方法

優先度は A ≫ B ＞ C。A を潰せば体感はほぼ解消し、B・C で堅牢性を上げます。

A リフレッシュを「1本化」する

並列に走る処理が同じリフレッシュトークンで一斉に交換をかけないよう、交換を直列化・重複排除（デデュープ）します。Lambda でインスタンスが散る前提なので、選択肢は3系統あります。

追加コストを避けたいなら → (b) が第一候補 (b) Supabase の refresh token reuse interval を数秒に設定すれば、お金の追加コストゼロ・コードほぼ無しで、同時多発の交換を実質1回にまとめられます。インスタンスをまたいでも効くのが利点。まずこれを入れ、足りなければ (a) を既存 Postgres の advisory lock（＝インフラ増なし）で足します。(c) は変更範囲が広く非推奨。
案追加コストコード変更根治力
(b) reuse intervalゼロ（設定トグル）ほぼ無し高
(a) 分散ロックPostgres advisory lock なら増なし / Redis は課金増中最も確実
(c) 入口を集約ゼロ（フロント改修大）大高
  • (a) 分散ロック / シングルフライト：短時間のロックを共有ストア（例：DB の advisory lock、あるいは Redis 等）に置き、リフレッシュ中は他は完了を待って新トークンを共有する。インスタンスをまたいでも効く本命の対処。
  • (b) リフレッシュの猶予（グレース）を許容：Supabase 側の設定で「ローテーション後も直前のトークンを数秒だけ有効」にする（refresh token reuse interval）。同時多発の交換を実質1回にまとめられ、コード変更を最小化できる。まず試す価値が高い。
  • (c) 交換の入口を1本に絞る：各処理が個別にリフレッシュせず、専用の「トークン更新エンドポイント」経由に集約し、フロント側で更新完了を待ってから本処理を投げる。
注意アプリのメモリ内 Promise デデュープ（同一インスタンス内の in-flight 共有）は同じ Lambda インスタンスに載ったリクエスト同士にしか効きません。改善はしますが、根治には (a) か (b) が要ります。

B Supabase クライアントを「状態レス」にする

サーバー用途では内部セッションを持たせない設定にします。ランタイムと E2E シードの不整合も解消します。

createClient(url, key, {
  auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
  global: { fetch: fetchWithTimeout },
})

これでインスタンス内の並行リクエストが内部セッションを共有せず、signOut の副作用も限定されます。トークンは Cookie で明示的に受け渡す今の方針とも整合します。

C 一過性エラーで即ログアウトしない

「トークン無効（401 相当）」と「到達不能・タイムアウト（5xx / ネットワーク）」を区別し、後者はログアウトさせずリトライ or 現行セッション維持にします。

// 例：エラー種別で分岐
const { data, error } = await supabase.auth.getUser(token)
if (error?.status === 401) return { kind: 'invalid' }   // 本当に無効 → refresh へ
if (error)                  return { kind: 'transient' } // 一過性 → 即ログアウトしない
return { kind: 'ok', user: data.user }

合わせて、リダイレクトで invalid_grant の連発が観測できるよう構造化ログを入れておくと、A の裏取りと再発監視ができます。

おすすめの進め方 ① まず A-(b)（Supabase の refresh token reuse interval を数秒に）で即効性を確認 → ② B（クライアントを状態レス化、低リスク）を同時投入 → ③ 必要なら A-(a)（分散ロック）で根治 → ④ Cで堅牢化。裏取りは CloudWatch Logs で invalid_grant と /login リダイレクトの相関を見るのが確実です。

用語解説

JWT（JSON Web Token）
「本人であること」等の情報に署名を付けた文字列。受け取った側は署名を検証するだけで本物と分かるため、毎回 DB を引かなくても認証できる。アクセストークンの実体がこれ。
アクセストークン / リフレッシュトークン
アクセストークンは短命（1時間）の「入館証」で毎リクエスト提示する。リフレッシュトークンは長命（30日）の「引換券」で、入館証が切れたとき新しいものと交換するために使う。
トークンのローテーション
リフレッシュトークンを1回使うと即座に無効化し、新しいリフレッシュトークンを併せて発行する方式。盗まれた券の再利用を検知・遮断できる代わりに、同じ券を2回使うと2回目が必ず失敗する。今回の競合の核心。
invalid_grant
OAuth/Supabase が「その引換券はもう使えません（無効・期限切れ・使用済み）」と返すエラー。ローテーション済みのリフレッシュトークンを使うとこれが出て、ログイン画面へ飛ぶ。
httpOnly Cookie
JavaScript から読めない Cookie。XSS でトークンを盗まれにくくするための保護。fumireply はトークンをこれで保存している。
レース条件（race condition）
複数の処理が同じ資源に同時アクセスして、実行順序次第で結果が壊れる不具合。今回は「同じリフレッシュトークンを同時に使う」レース。
排他制御 / デデュープ / シングルフライト
同時に走る処理を1本にまとめる仕組み。「今リフレッシュ中なら他は待って結果を共有する」ようにすると、券の二重使用を防げる。
ステートレス（Lambda）
関数がリクエスト間でメモリ状態を保持しない性質。スケールしやすい反面、「今処理中」を共有メモリで管理できないので、ロックは外部ストア（DB/Redis 等）に置く必要がある。
同時実行 / コールドスタート（Lambda）
同時実行：複数リクエストを別インスタンスで並行処理すること（今回は並列リフレッシュの温床）。コールドスタート：新インスタンス起動時の初回遅延で、一過性のタイムアウトを招きやすい。
singleton
1つのインスタンスを使い回す設計。getSupabaseClient() がこれ。ただし Lambda インスタンスごとに別の singleton になる点に注意（グローバルに1つではない）。
